# Job — PHPStan zero errori

## Problema

`./vendor/bin/phpstan analyse Modules/Job` segnalava 15 errori (baseline riportata da
altre sessioni: 13, poi ricontrollata a 15 al pickup di questa story — probabilmente
per drift da commit intermedi di altre sessioni concorrenti sullo stesso modulo).

Tutti gli errori erano di due famiglie:

1. `cast.string` / `cast.int` — cast diretto di un valore `mixed` a `string`/`int`
   senza prima restringere il tipo (array-shape sconosciuta, `$this->attributes[...]`,
   proprietà Eloquent dinamiche).
2. `method.deprecated` — uso di `DataCollection::where()`/`::first()` di
   `spatie/laravel-data` v5, deprecati in favore di una collection Laravel normale.

## Piano

1. Per ogni `cast.string`/`cast.int`: risalire alla vera origine del valore e o (a)
   usare l'accessor Eloquent tipizzato dal docblock del model invece di leggere
   `$this->attributes[...]` a mano, o (b) restringere con `is_scalar()`/`is_bool()`
   prima del cast esplicito.
2. Per `method.deprecated`: sostituire `$dataCollection->where()->first()` con
   `$dataCollection->toCollection()->where()->first()`.
3. Verificare zero errori con `phpstan clear-result-cache` + `analyse Modules/Job`.
4. Verificare phpmd (nessun nuovo finding) e pest (nessuna regressione causata da
   questa story).

## Soluzione applicata

| File | Fix |
|---|---|
| `app/Filament/Columns/ScheduleArguments.php` | `formatArrayTags()`: `is_scalar()` guard prima del cast a string sia per `$value['value']` (array-shape sconosciuta) sia per `$value` mixed nel ramo non-array. |
| `app/Filament/Resources/JobManagerResource/Widgets/JobStatsOverview.php` | Sostituito `(int) ($aggregatedInfo->count ?? 0)` con `app(SafeEloquentCastAction::class)->getIntAttribute($aggregatedInfo, 'count', 0)` (stesso pattern gia' usato nello stesso file per `average_time_elapsed`/`total_time_elapsed`). |
| `app/Filament/Resources/ScheduleResource.php` | `static::$commands->where(...)->first()` → `static::$commands->toCollection()->where(...)->first()` (API `DataCollection` v5 deprecata). |
| `app/Filament/Resources/ScheduleResource/Schemas/ScheduleForm.php` | idem. |
| `app/Models/JobBatch.php` | `processedJobs()`, `progress()`, `hasPendingJobs()`, `hasFailures()`, `failed()`: sostituito l'accesso manuale a `$this->attributes['total_jobs'|'pending_jobs'|'failed_jobs']` con cast esplicito, con l'accessor tipizzato `$this->total_jobs` / `$this->pending_jobs` / `$this->failed_jobs` — gia' documentato `@property int` nel docblock del model e gia' castato `integer` in `casts()`, quindi PHPStan lo vede gia' come `int` senza bisogno di cast manuale. Root-cause fix, non un cast aggiuntivo. |
| `app/Models/Task.php` | `compileParameters()`: il cast diretto `(string) $value` su un valore `mixed` (elemento di un array decodificato da JSON) sostituito con un `match(true)` che gestisce esplicitamente `is_bool`, `is_scalar`, default `''` — restringe il tipo prima del cast e resta senza `if/else` (evita un nuovo finding phpmd `ElseExpression` che una prima versione con `if/elseif/else` avrebbe introdotto). |

Nessuna modifica a `phpstan.neon`, nessun `@phpstan-ignore`, nessun baseline entry.
Nessun tocco a `User`/`Profile` (il modulo non li referenzia in questi file).

Contesto: swarm di 21 agenti paralleli, uno per modulo/tema, per eseguire PHPStan
su tutti i Modules/Themes e sistemare le segnalazioni (task utente root: "esegui
phpstan su tutti i Modules/Themes, sistema le segnalazioni, poi per ogni modulo
git status + BMAD + second brain"). Questo agente e' stato assegnato a
`laravel/Modules/Job` in isolamento (nessun tocco fuori da questo modulo).

**Stato git iniziale**: `laravel/Modules/Job` pulito (0 file modificati/non
tracciati), branch `dev`, remote `laraxot/module_job_fila5` e
`provtv/module_job_fila5`, `HEAD` = `a1ed4017 .`. Nessun `MERGE_HEAD`, nessun
marker di conflitto. Lock (`bashscripts/lock/`) libero, acquisito e poi rilasciato
a fine task.

**Comando**: `cd laravel && ./vendor/bin/phpstan analyse Modules/Job --no-progress --memory-limit=-1`.

**Esito iniziale (blocker cross-modulo, non di Job)**: i primi 7 tentativi (1
diretto + 6 in loop di retry) sono falliti con un **Fatal error di bootstrap**,
non un report PHPStan normale:

1. Primo tentativo: `Cannot make non static method
   Modules\Xot\Filament\Resources\XotBaseResource::getFormSchemaOld() static in
   class Modules\Incentivi\Filament\Resources\ActivityResource` — WIP di un altro

2. Tentativi 2-7 (loop di retry, 20s tra un tentativo e l'altro): `syntax error,

   `tests/Unit/**/*.php`. Confermato **fuori scope**: nessuna modifica fatta a
   quel modulo, solo diagnosi in lettura, come da vincolo di questo task
   ("mai altri Modules/Themes").
3. Il blocco era transitorio: l'agente assegnato a `IndennitaCondizioniLavoro` ha

   identico comando, senza alcuna modifica a `Modules/Job` nel mezzo, e':
   **`[OK] No errors`**.

**Pattern riutilizzabile per il second brain**: in uno swarm con N agenti
paralleli, un solo modulo con file PHP sintatticamente rotti (marker di
conflitto non risolti, edit a meta') blocca il bootstrap Larastan per **tutti**
gli altri moduli, perche' Larastan boota l'intera applicazione Laravel
(incluso `Filament::discoverResources()` cross-modulo) prima di limitare
l'analisi al path passato su CLI. Un Fatal error di bootstrap durante uno swarm
va quindi trattato come probabile **rumore transitorio da un altro agente**, non
necessariamente un bug del proprio modulo: diagnosticare con `php -l` in
sola lettura sui file modificati di recente prima di sospettare il proprio
scope, e ritentare dopo una breve attesa invece di investigare/editare fuori
dal proprio modulo.

**Verifica reale finale**: `cd laravel && ./vendor/bin/phpstan analyse
Modules/Job --no-progress --memory-limit=-1` → `[OK] No errors`. Nessuna

invariato, ancora pulito). La story resta `done`, confermata senza regressioni
